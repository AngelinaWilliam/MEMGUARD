What MemGuard X can and cannot see
  exact     : open.mp pool entities (counts only, no byte sizes), script-reported allocations
              (MemGuard_TrackAlloc: counts and the sizes the script reports), timers, DB handles,
              AMX heap/stack usage of each script
  measured  : process resident/private memory; C heap in use / free-retained (glibc mallinfo2).
              Whole-process numbers: they include every component and plugin and cannot be
              attributed to individual allocations.
  not seen  : allocations made inside other components/plugins or the server, per-player
              objects/textdraws, memory of data structures inside the AMX beyond heap/stack usage,
              allocator internals. A leak there shows up only as process/heap growth.
  rule      : an active allocation is never reported as leaked; only sustained growth after warm-up is
              flagged as a possible leak, and only double/unknown frees are confirmed tracking errors.

Notes: 'active' tracked allocations are not leaks by themselves. 'POSSIBLE LEAK' means sustained growth
across snapshots and needs investigation. Only double/unknown frees and duplicate allocations are confirmed
tracking errors. Native times are inclusive of anything the native itself executes (e.g. CallLocalFunction).
